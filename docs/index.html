Kubernetes Fundamentals for Beginners

Core concepts explained simply with real-world analogies.

Pod (The Container Wrapper)

The smallest deployable unit. Think of a Pod as a pea pod holding one or more tightly coupled container peas. Containers in a Pod share the exact same network IP and storage volumes.

myapp Pod (Port 8080)

Deployment (Self-Healing)

A manager that tells Kubernetes: "Ensure 2 copies of my container are always running." If one container dies or a server crashes, the Deployment immediately launches a new one.

replicas: 2

Service (Stable Gateway)

Pods get new IP addresses whenever restarted. A Service provides a single, permanent IP address and DNS name (`myapp.default.svc`) that load balances traffic across all backend Pods.

ClusterIP / LoadBalancer

Ingress (Traffic Director)

The smart door attendant. Routes incoming domain names (like `ex6.aiguru.website` or `ex9.aiguru.website`) and URL paths to the appropriate internal Kubernetes Service.

alb / external-nginx

The 6-Stage Inbound Packet Lifecycle (Internet to Pod)

How requests navigate from public DNS to private container network interfaces.

1 DNS Resolution

The user types https://ex7.aiguru.website. GoDaddy delegates authority to AWS Route 53, which resolves the CNAME to the public DNS hostname of the AWS Load Balancer.

2 AWS Edge & IGW

Traffic reaches AWS edge infrastructure protected by AWS Shield Standard (DDoS mitigation). The Internet Gateway (IGW) translates the public destination IP to the internal AWS network.

3 Firewall & Security Groups

Subnet NACLs and Load Balancer Security Groups inspect the packet. Inbound traffic is allowed strictly on ports 80 and 443; all unauthorized ports are dropped at the edge.

4 Public Subnet Ingestion

Load Balancer nodes live in Public Subnets (10.0.64.0/19 & 10.0.96.0/19) across 2 Availability Zones for high availability and load distribution.

5 Private Subnet Transit

The Load Balancer forwards traffic into the Private Subnets (10.0.0.0/19 & 10.0.32.0/19). Worker node Security Groups permit traffic only from the Load Balancer security group.

6 Pod Delivery via VPC CNI

Because target groups use target-type: ip, traffic routes directly to the Pod's private IP (10.0.x.x) allocated by AWS VPC CNI, eliminating NodePort and kube-proxy overhead.

Layer 7 HTTP routing using AWS Application Load Balancer. Inspects Host headers (ex6.aiguru.website) and URL paths, performing health checks on /health.

Option 3: ALB + HTTPS (ACM) Example 7

Enterprise SSL offloading at AWS edge. ALB terminates TLS 1.3 using an AWS ACM certificate (*.aiguru.website) and auto-redirects HTTP:80 → HTTPS:443.

Protocol: HTTPS:443 (with 301 Redirect)
TLS Termination: AWS ALB Hardware (Edge)

Tested: curl -v https://ex7.aiguru.website
Option 4: Ingress-NGINX (HTTP) Example 8

Kubernetes-native ingress controller. AWS NLB passes TCP:80 directly to NGINX pods in the cluster, which evaluate routing rules and proxy traffic to backend services.

Protocol: TCP:80 → HTTP Layer 7 NGINX
TLS Termination: None (Plaintext HTTP)
Controller: Ingress NGINX (Helm 16)
K8s Resource: Ingress (ingressClassName: external-nginx)
Tested: curl http://ex8.aiguru.website
Option 5: Ingress-NGINX + Cert-Manager (Let's Encrypt TLS) Example 9

100% automated, zero-touch Kubernetes PKI. AWS NLB passes encrypted TCP:443 to Ingress-NGINX. Cert-Manager automates ACME HTTP-01 challenge verification, requests free certificates from Let's Encrypt, writes TLS keys into Kubernetes Secrets (ex9-aiguru-website-tls), and auto-renews them.

Protocol: HTTPS:443 (End-to-End)
TLS Termination: Ingress-NGINX Pods (Cluster)
Certificate Authority: Let's Encrypt (Public CA)
Automated Solver: ACME HTTP-01 (/.well-known/acme-challenge)
Tested: curl -v https://ex9.aiguru.website

Defense-in-Depth Security & Firewall Rules

How AWS and Kubernetes isolate private worker nodes from direct internet exposure.

1. Perimeter Firewalls (Edge)
  • AWS Shield Standard: Always-on L3/L4 DDoS mitigation.
  • Internet Gateway: Allows public traffic only destined for public subnet load balancers.
  • Subnet NACLs: Stateless boundary packet filtering.
2. Security Groups (Stateful)
  • ELB Security Group: Permits Inbound Port 80 & 443 from 0.0.0.0/0.
  • Worker Node Security Group: Forbids direct internet connections! Permits inbound traffic only from the ELB Security Group or VPC CIDR.
3. Private Subnet Isolation
  • Zero Public IPs: Worker nodes and application pods never receive public IP addresses.
  • Private Route Tables: Only route outbound default traffic (0.0.0.0/0) to the NAT Gateway.
  • Zero Attack Surface: Attackers on the internet cannot scan, ping, or connect directly to any node or pod.

Domain, DNS & SSL Architecture (aiguru.website)

Complete prerequisite guide: Delegating GoDaddy DNS to AWS Route 53, provisioning AWS ACM certificates, configuring Cert-Manager with Let's Encrypt, and routing traffic across ALB and NGINX Ingress controllers.

Why You MUST Complete These Steps Before Running Examples 6-9

In Examples 6, 7, 8, and 9, applications are exposed to the public internet using custom subdomains under aiguru.website. Because the domain was purchased on GoDaddy, internet DNS queries initially hit GoDaddy's default nameservers. For AWS Load Balancers, AWS Certificate Manager (ACM), and Cert-Manager to operate seamlessly, you must delegate authoritative DNS to AWS Route 53 and provision the required SSL certificates before deploying the ingress manifests.

Path A: Cloud-Native AWS ALB + ACM (Ex 6 & 7) DNS CNAME -> AWS ALB -> Edge TLS terminated with AWS Certificate Manager in eu-north-1 -> Direct Pod IP.
Path B: Kubernetes-Native NGINX + Cert-Manager (Ex 8 & 9) DNS CNAME -> AWS NLB (L4) -> NGINX Ingress -> Cert-Manager ACME HTTP-01 automated Let's Encrypt SSL.

Create AWS Route 53 Public Hosted Zone

Creates the authoritative DNS zone in AWS for aiguru.website and generates your 4 AWS Name Servers.

Method A: AWS Management Console
  1. Log in to the AWS Management Console and search for Route 53.
  2. Click Hosted zones in the left sidebar, then click Create hosted zone.
  3. Under Domain name, enter: aiguru.website.
  4. Under Type, ensure Public hosted zone is selected.
  5. Click Create hosted zone at the bottom.
  6. Once created, open the zone and find the record of type NS (Name Server).
  7. Copy all 4 AWS Name Servers (e.g., ns-xxxx.awsdns-xx.org).
Method B: AWS CLI (on k8s-client)

Run this command on your EC2 management host to create the zone instantly:

aws route53 create-hosted-zone   --name "aiguru.website"   --caller-reference "$(date +%s)"   --hosted-zone-config Comment="Hosted zone for EKS demo cluster"

# Query your 4 assigned Name Servers:
aws route53 list-resource-record-sets   --hosted-zone-id $(aws route53 list-hosted-zones-by-name --dns-name "aiguru.website" --query "HostedZones[0].Id" --output text)   --query "ResourceRecordSets[?Type == 'NS'].ResourceRecords[*].Value"   --output table

AWS Certificate Manager (ACM) Setup (Required for Example 7)

Provisions a free wildcard SSL certificate for *.aiguru.website in region eu-north-1 (Stockholm).

Why ACM is Required for Example 7:

In 7-example, the AWS Application Load Balancer terminates TLS on port 443 at the AWS edge before proxying plaintext traffic into the private cluster. AWS ALB cannot read Kubernetes secrets; it requires an SSL certificate registered in AWS Certificate Manager (ACM) in the exact same AWS region as the ALB (eu-north-1).

Request Certificate via AWS Console:
  1. Make sure your AWS Console region is set to Stockholm (eu-north-1).
  2. Search for Certificate Manager and click Request a certificate.
  3. Select Request a public certificate → click Next.
  4. Domain names:
    • Primary: *.aiguru.website
    • Add another: aiguru.website
  5. Validation method: select DNS validation - recommended.
  6. Key algorithm: select RSA 2048 → click Request.
  7. Click into the new Certificate ID → click Create records in Route 53 → click Create records.
  8. Within 2 to 5 minutes, status changes to Issued!
Update 7-example/3-ingress.yaml with your ARN:

Once issued, copy the Certificate ARN and paste it into the ingress annotation:

# File: 7-example/3-ingress.yaml
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: myapp
  namespace: 7-example
  annotations:
    alb.ingress.kubernetes.io/scheme: internet-facing
    alb.ingress.kubernetes.io/target-type: ip
    alb.ingress.kubernetes.io/listen-ports: '[{"HTTP": 80}, {"HTTPS":443}]'
    alb.ingress.kubernetes.io/ssl-redirect: "443"
    # REPLACE WITH YOUR ACTUAL ACM ARN IN eu-north-1:
    alb.ingress.kubernetes.io/certificate-arn: arn:aws:acm:eu-north-1:619544673475:certificate/<YOUR-CERT-UUID>
04

Cert-Manager & Let's Encrypt Setup (Required for Example 9)

Zero-touch automated public SSL issuance via ACME HTTP-01 challenge inside Kubernetes.

How the ACME HTTP-01 Integration Works:

Unlike Example 7 which offloads TLS onto AWS ALB, Example 9 uses the Kubernetes-native Cert-Manager controller (installed via 17-cert-manager.tf) and the Ingress-NGINX controller (installed via 16-nginx-ingress.tf).

  1. When you apply 9-example/0-cluster-issuer.yaml, Cert-Manager registers an ACME account with Let's Encrypt production.
  2. When you apply 9-example/4-ingress.yaml with annotation cert-manager.io/cluster-issuer: http-01-production, Cert-Manager requests a certificate for ex9.aiguru.website.
  3. Let's Encrypt gives Cert-Manager a challenge token and attempts an HTTP GET on http://ex9.aiguru.website/.well-known/acme-challenge/<TOKEN>.
  4. MANDATORY: A CNAME record for ex9.aiguru.website MUST point to the NGINX NLB so Let's Encrypt can reach Cert-Manager's challenge pod!
  5. Once validated, Let's Encrypt signs the certificate, and Cert-Manager saves it into Kubernetes Secret ex9-aiguru-website-tls.
Commands to Monitor & Debug Certificate Issuance: 
# 1. Watch Certificate status (READY should transition from False -> True):
kubectl get certificate -n 9-example -w

# 2. Inspect Certificate Request details:
kubectl get certificaterequest -n 9-example

# 3. If validation hangs, inspect the ACME Challenge object:
kubectl get challenge -n 9-example
kubectl describe challenge -n 9-example

# 4. Verify the generated TLS Secret inside Kubernetes:
kubectl get secret -n 9-example ex9-aiguru-website-tls

Production Troubleshooting Field Guide

Diagnosis and solutions for common Kubernetes and AWS EKS failures.

Pods stuck in `Pending` State

Scheduling Failure

Cause: Insufficient CPU/Memory on worker nodes, or EC2 ENI IP address exhaustion (e.g. running `t3.small` with 18 system pods).

kubectl describe pod <pod-name> -n <namespace>
# Look for: "0/2 nodes are available: 2 Insufficient cpu."

Fix: Upgrade instance type in `8-nodes.tf` to `t3.large` (supports 35 pods) and scale node group: `desired_size = 2`.

Add-on / Helm 20m Timeout in Terraform

Dependency Deadlock

Cause: Helm attempted to install charts before worker nodes joined the cluster, or nodes in private subnets could not reach Docker Hub because NAT Gateway routing was missing.

depends_on = [aws_eks_node_group.general, aws_eks_addon.pod_identity]

Fix: Add explicit `depends_on` clauses linking add-ons to the node group, and ensure private subnets route to `aws_nat_gateway.nat`.

Let's Encrypt Certificate Stays `False`

ACME Challenge Failure

Cause: `ex9.aiguru.website` does not resolve to the external NGINX NLB IP, or port 80 is blocked by security groups.

kubectl describe challenge -n 9-example
kubectl describe certificate ex9-aiguru-website-tls -n 9-example

Fix: Add a CNAME record in your DNS manager pointing `ex9` to the exact Load Balancer hostname returned by `kubectl get svc -n ingress external-ingress-nginx-controller`.

Secrets Store CSI Driver: Mount Failure

IRSA Trust Error

Cause: AWS region mismatch (`us-east-2` vs `eu-north-1`) in `SecretProviderClass`, or IAM Role ARN in ServiceAccount belongs to another AWS account.

kubectl describe pod -n 12-example <pod-name>
# Look for: "failed to get secret: AccessDeniedException"

Fix: Ensure `region: eu-north-1` in `1-secret-provider-class.yaml` and verify service account annotation matches your account: `arn:aws:iam::619544673475:role/staging-demo-myapp-secrets`.
